# 我们还没解决的 5 个问题

> Agent 生产化手记 · 08
>
> **系列导读**：本系列尝试回答一个具体问题——当 Agent 不再是一次请求，而是一个可能持续几十分钟、会中断、会失败、要花钱、要被人看懂的有状态长事务时，生产系统该一条一条补上什么。
>
> - **第一篇**：能跑 10 分钟和能上线 10 个月，差在 Agent 是一笔有状态的长事务，上线就是把这笔事务该有的东西补齐。
> - **第二篇**：向人提问时，这一轮怎样提交成等待，刷新和隔天再答都还能接上。
> - **第三篇**：子 Agent 删了三次，因为它是另一笔事务，多数能力只是当前这一轮里的过程。
> - **第四篇**：接入和执行拆开，开单、回放和把这一轮跑完，不再绑在同一个进程上。
> - **第五篇**：事实、传输、恢复点、执行现场分开存，Checkpoint 不能当作数据库。
> - **第六篇**：成功、中断、取消、异常收成同一个提交点，执行不能靠重试再做一遍。
> - **第七篇**：254KB 的记忆怎样烧掉十几万 token，这笔预算取决于注入多少、何时注入、谁来写。
> - **第八篇（本文）**：轮次账本、租约、公平队列、能力评测、文档五处还没补上，现状离那句话还有多远。

内测阶段，最怕被问一句话：你们这个能上线吗？

我们的回答一直是：能跑，但还有几个洞。

这篇就把洞摊开说。不是自谦，是因为下面这五个问题，我们每天都在绕，还没填上。

---

## 一、轮次没有账本

系统里，"一轮对话"只是一个编号，不是一个实体。

数据库里只有会话的当前状态和"活跃轮次是第几轮"，真正的轮次 id 只活在 Redis 里。

后果很具体：进程被 kill 之后，巡检知道"这个会话卡住了"，但不知道卡在哪一轮。它得反过来查"最近落库的那条消息属于哪一轮"，才能补一条错误记录。如果这个会话还没有任何消息落库，它就补不了，只能把会话置成异常，剩下的靠用户刷新。

我们想补的是一张轮次表：每轮一行，记 id、状态、开始时间、执行者。这样巡检不用猜，重试不用猜，排查也不用猜。

这件事不难，难的是它要动最核心的写入路径，而我们还在内测，不敢在流量上做大手术。

现在每加一个恢复逻辑，都要先想一遍"如果此时轮次 id 丢了怎么办"。

---

## 二、心跳没有租约

判活用的是"心跳 key 还在不在"。简单，够用，但它有一个前提：**只有一个进程在续期。**

这个前提我们破过一次。

有一次滚动更新，旧进程还没完全退出，新进程已经起来了。两个执行者同时认为自己是这一轮的主人，心跳互相覆盖。巡检看到 key 一直在，就认为一切正常；实际上两个进程在抢同一份状态。

后来我们加了防护：续期统一登记、巡检在 key 丢失时反查最近消息、被替换的轮次立刻取消。但这些都是补丁，不是租约。

真正的租约要有两样东西：一个递增的持有者编号（fencing token），和每次写入时的条件更新。这样旧主即使还活着，它的写也会被拒绝。

我们还没有做。现在的方案能扛住已知的几种情况，但我不敢说它能扛住所有情况。

最坏的情况是：用户看到内容重复，或者同一个操作被执行两次。

---

## 三、没有公平队列

任务队列是全局的，并发上限也是全局的。

这意味着：一个用户的长任务，可以把并发槽吃满，其他用户排队。

内测阶段人少，这个问题不明显。但它是个定时炸弹——用户一多，"某个人的大任务拖慢所有人"一定会发生。

要补的话，至少三件事：按用户的并发配额、任务优先级（短任务别排在长任务后面）、以及一个能看见排队深度的监控。

---

## 四、没有能力评测（最大的洞）

前面七篇里提到的那些改造，都有明确的技术方案。这一个没有。

我们有几百个测试，覆盖接口、轮次、沙箱、工具、恢复。全是**功能正确性**测试：这个东西能不能跑通。

但我们没有**能力评测**：改一版提示词，模型是变好了还是变坏了？换一个模型，任务成功率掉了几个点？调了中间件顺序，工具调用次数是多了还是少了？

现在全靠人肉体感。

这意味着两件事：

第一，我们不敢大改提示词。因为改完不知道会不会退步，只能靠几个人试几条对话。

第二，所有"优化"都缺乏证据。我们前面写的那些改造——拆分、压缩、按需加载——能说清楚"更快了""更省了"，但很难说清楚"更准了"。

我们想做的是一套很小的评测：几十条真实任务，每条有期望的工具序列和期望的产物；用规则断言加模型判分双轨；跑在 CI 里，改提示词必须先过它。

听起来不难，做起来很脏：任务要脱敏、判分要不稳定、期望值要维护。这也是为什么它一直排在最后。

但它是从"能跑"到"敢改"的分水岭。没有它，我们对 Agent 的每一次调整，本质上都是盲改。

更麻烦的是，没有评测，我们连"这次改动值不值得"都说不清——只能说"感觉快了一点"。

---

## 五、文档在漂移

最后一个洞最不技术，但最耗人。

仓库里有一份架构文档，还在描述一个早就不用的运行时；有几个函数的注释，还在引用已经被删掉的调用方；配置文件里有一整段没人读的参数。

这些不是"文档没更新"，是**文档和代码各自演化，最后变成了两个版本的事实**。

新人进来，先读文档，然后被代码打脸；老人改代码，忘了改文档，下一个人再被打脸。

我们试过用规则约束（改代码必须同步改注释），有一点用，但不多。

有一次新人按文档改配置，改完服务起不来——文档里那条路径已经不存在了。这种事发生两次之后，大家就默认"文档只能当参考"，然后文档就彻底没人维护了。

真正有用的可能是让文档从代码里长出来——至少那些"谁调用了谁""这个字段谁在读"的部分。

---

## 六、还有三个小洞

- **记忆读写分叉**：写入在轮次收尾，读取在下一轮提交。这一轮沉淀的东西，下一轮才用得上；恢复的轮次甚至不走预取。
- **主链路和 A2A 不对等**：A2A 调用有工具，但没有每轮的预取和上下文块。同一套能力，两个入口，行为不完全一致。
- **压缩不可逆**：历史被压成摘要之后，原文只留在数据库里，模型再也看不到。

---

## 七、如果重来一次

如果只能按顺序补，我们的排法是：轮次账本 → 租约 → 评测 → 公平队列 → 文档。前两个是地基，第三个是刹车，后两个要等规模上来才会真疼。

```mermaid
flowchart LR
    A["1 轮次账本<br/>地基"] --> B["2 租约<br/>地基"]
    B --> C["3 能力评测<br/>刹车"]
    C --> D["4 公平队列<br/>规模"]
    D --> E["5 文档<br/>交接"]
```

*图 1：补洞的顺序。前两个不做，后面全是补丁。*

图上是五个洞之间的依赖。下面三件是相对实际做法会提前的事，不替代这张顺序。

如果重来一次，有三件事我们会提前做：

第一，先有评测，再改提示词。哪怕只有二十条任务，也比没有强。

第二，先把轮次做成一张表，再谈调度。后面所有恢复逻辑都受它影响。

第三，把提示词当配置，不当代码。它改得比代码勤，发布节奏却绑在代码上。

## 八、按那句话打个分

第一篇的定义是：Agent 是一个会持续、会中断、会失败、要花钱、要被人看懂的有状态长事务。生产化就是把这几项补齐。走到第八篇，可以打个分。

| 要补的一项 | 已经有的 | 还没有的 |
| --- | --- | --- |
| 有状态 | 事实、传输、恢复点、现场分开；接入层不读 checkpoint | 轮次账本；恢复点丢了，不能从事实重建 |
| 会中断 | 开单与回放分开；等人是一轮的合法终态 | 实时和回放的形状还靠人测，没有自动校验 |
| 会失败 | 四种结束走同一个提交点；错误能回放；假死有巡检 | 租约，仍可能出现两个执行者；公平队列 |
| 要花钱 | 记忆按需检索，写收到收尾；技能分三层加载 | 统一配额；记忆只增不删；压缩不可逆 |
| 要被人看懂 | trace、错误码、耗时和积分随回放走 | 能力评测；文档和代码仍是两套事实 |

有状态和会中断，常见故障能扛住。会失败有了统一出口。要花钱不再全量注入。要被人看懂，出了事能查，改了还不知道有没有变好。

这就是内测的水平：敢让一批真实用户用，出了问题能查、能修、能说明白。

---

## 九、最后

八篇留一句：

**Agent 不是一次请求，是一个可能持续几十分钟、会中断、会失败、要花钱、要被人看懂的有状态长事务。生产化，就是一条一条把这种长事务该有的东西补齐。**

这句话先改变提问的顺序：先问这一轮怎么结束，再问提示词怎么写。这篇是还没补完的几条。前两个洞不补，恢复逻辑会继续猜；评测不补，提示词就只能盲改。

系统还在内测。五个洞会一个一个填。文档那一条尤其想听别人怎么做：怎样让说明和代码不要变成两套事实。
