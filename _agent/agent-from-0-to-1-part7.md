有用户反馈：最近变慢了。

桌面端和浏览器一起慢。首字要等二十五到四十秒。我们先查模型，再查网络，再查网关。慢发生在模型还没开始回答之前：提示词送出去的那一下，时间已经花掉了。

那个用户的长期记忆是一个 254KB 的文件。每一轮都整份拼进系统提示词，大约 14 万 input token。模型还没看见这一轮的问题，先把一本日记读完。

[第六篇]({{ '/agent/agent-from-0-to-1-part6/' | relative_url }})让一轮能干净地停下来。停下来之后，下一轮会把留下来的东西再读进去。读进去多少，就是这一轮的账单。

## 一、想记住的，和实际写进去的

做记忆的初衷很小：记住偏好、常用参数、上次的选择，别每次都重新问。

第一版都是这两段：

```python
def build_prompt(user_id, user_text):
    memory = read_file(f"memory/{user_id}.json")   # 不看 user_text，整份读
    return system_prompt + memory + user_text

def after_round(user_id, messages):
    memory = read_file(f"memory/{user_id}.json")
    memory += llm.extract("这轮有什么值得记住的", messages)  # 模型自己决定写什么
    write_file(f"memory/{user_id}.json", memory)             # 只追加，不删
```

读不看这一轮在问什么。写不看这条值不值得留下。文件只增不减，也没有上限。模型很勤奋，一次性的确认、临时参数、任务做到一半的状态，都会被它当成"值得记住"。几个月后，单个用户涨到 254KB。

用户感到的慢，发生在所有客户端上，因为贵的是同一次模型调用，不是某一个界面。254KB 坐在提示词最前面，把这一轮真正要问的话挤到后面，也把费用先计上。

两处错绑在一起：**读的时候不筛选，写的时候不设防。** 只改存储，这两处还在，文件会换成另一本同样厚的日记。

## 二、四代，砍的是读和写

| 代 | 做法 | 为什么换掉 |
| --- | --- | --- |
| 一 | 自己写的 JSON 分桶，模型主动往里追加 | 有字段，但没有上限，写什么凭模型自觉 |
| 二 | 换成框架自带的记忆文件，每轮全量注入 | 纯文本，连字段都没了，只能整份读，涨得更快 |
| 三 | 出事当天关掉注入，改接独立记忆服务 | 先让对话恢复，接受暂时想不起来 |
| 四 | 按这句话检索，写入收到轮次收尾 | 现在这一代 |

第二代看起来更"标准"，读路径却更死。分桶好歹还能按字段挑。纯文本没有可挑的边，注入函数只剩一种实现：全部拼进去。所以它不是小改，是把第一代的无界增长换成了更难筛选的无界增长。

第三代是止血，不是方案。254KB 已经在线上。当天把注入关掉，首字回到正常。用户暂时失去"它还记得我"，但二十五秒的等待先消失。独立记忆服务是在这之后接上的。顺序不能反：先把档案从寄存器里拿出去，再谈怎么按需拿回来。

第四代对那两处各砍一刀。

**读改成按需。** 每轮只用用户这句话去检索，命中几条就注入几条。254KB、14 万 token，变成最多三五条，几百 token。记忆不是文档，三五条够改变这一轮的判断；再多，挤的是当前任务。

读留了两条路，写只有一条：

</div>

*图 1：读可以发生两次，写只发生在收尾。模型能查，不能自己往库里追加。*

预取保证不用特意问也能想起来。工具保证它想核对细节时还有入口。两条路都从同一份记忆库读，避免提示词里一份、工具里另一份。

**写从模型手里收回来。** 模型不再有"写记忆"的工具。一轮结束，系统拿这一轮的用户消息和助手回复，交给记忆服务提取事实。输入用的是这一轮已经发生的对话，不去 checkpoint 里把整份运行时状态捞回来——[第五篇]({{ '/agent/agent-from-0-to-1-part5/' | relative_url }})那份 blob 会压缩，也会把收尾拖慢。[第六篇]({{ '/agent/agent-from-0-to-1-part6/' | relative_url }})把收尾收成一个入口之后，提取才能挂在这个入口上，而不是散在每条结束路径里。

写比读更要紧。只要模型还能自由写，检索只是在一堆流水账里挑。一次性确认、临时参数、做到一半的状态会继续进库。记忆应该是沉淀下来的事实。流水账留在消息表里，那是给人回放的，不是给下一轮预取的。

代价也实在。现在没有遗忘，只增不删。用户没有入口去看，也没有入口去删。这一轮收尾写下的事实，要到下一轮提交才进得了预取；从 checkpoint 恢复、接着跑的那一轮，甚至不走预取。时间差还在。[第八篇]({{ '/agent/agent-from-0-to-1-part8/' | relative_url }})把这个口记在还没补的清单里。

## 三、存哪儿不是那三个问题

我们一开始以为要争论的是文件还是数据库、自己写还是用现成服务。四代换了三次存储，事故的形状没变，直到读和写的规则变了。

真正要先答的是三句：

1. **注入多少。** 全量还是前几条。这一条决定 14 万还是几百，也决定首字是二十五秒还是正常。
2. **什么时候注入。** 提交时预取，还是等模型自己调用检索。预取会干扰当前任务，不预取就会在该想起来的时候失忆。两条都留着，是因为只留一条都会漏。
3. **谁有权写。** 模型写，库会变成流水账。系统在收尾时写，写进去的才是这一轮结束后还成立的事实。

存储要回答的是这三句的实现。三句没写下来，换到哪里都会把整本档案再塞进提示词。

## 四、同一个月，上下文还在另外三处漏钱

记忆只是预算的一块。同一段时间，另外三处用不同的办法把窗口撑破。

**中文压缩不触发。**

压缩中间件用"四个字符大约一个 token"估计用量，再和模型输入上限的 85% 比。英文大致够用。中文差一截：一千多个汉字，它估 289，按模型自己的分词是 780，低估 2.7 倍。估算值永远爬不到 85%，压缩一次都不跑。上下文一直涨，直到模型直接拒绝。

后来换成按这个模型校准的分词器，图片另计一笔固定成本。触发仍是到 85%，保留最近 10% 的原文。这两个数来自窗口大小，以及"最近几轮必须还能看见原话"。尺子先校准，阈值才有意义。计费不用这把尺子，计费用模型返回的 usage。估算只负责"要不要压缩"。

**一张照片被当成一段超长文本。**

工具读图片，返回的是图片。某个模型适配层把工具结果序列化成字符串，base64 就从图片变成了文本，按字符计进上下文。一张 317KB 的照片，一次调用大约 30 万 token，吃掉窗口的六成。[第一篇]({{ '/agent/agent-from-0-to-1-part1/' | relative_url }})里那笔"要花钱"，就是这一次。

修好之后，同一张图大约 242 个图片 token。差了一千多倍。这不是把图片压小了，是让它重新按图片计。在这之前，预算系统看见的是一段不该存在的文本。

**输出上限把工具参数切断。**

单轮输出上限当时是 16K，思维链和正式输出共用这一格。一类轮次会同时占满它：想得很长，然后一次写一个大文件。文件正文躺在工具参数里，也是输出 token。额度在 JSON 中间被截断，模型收到残缺参数，报错，重试，再截断。短对话里各看各的，都在额度内，所以几个月对不上。

上限调到 64K 之后这批轮次才稳住。共享的还是同一个计数器。再长的思考、再大的写入，同一刀还会落下。64K 把截断推出了当时的样本，没有把两样东西拆开计量。

## 五、技能也是按次付费的上下文

技能说明是另一本会被整本塞进来的书。

一开始，名字、描述、用法全部进提示词。技能一多，光目录就是几千 token，其中大部分和这一轮无关。模型要在一堆用不上的说明里找当前该用的那一条，找到了也已经付过全部的钱。

后来分成三次加载，用到哪一层才付哪一层：

- 提示词里只放技能名，加一句不超过 50 字的摘要，让它知道"有什么"；
- 需要细节时调用检索，只返回摘要列表，不给全文；
- 确定要用，才把完整说明取出来。

![技能分三次加载，用到才付全额]({{ '/assets/images/agent/agent-from-0-to-1/p7-02-skill-layers.png' | relative_url }})

*图 2：前两次只付目录的钱。全文出现在第三次，而且只出现被选中的那一份。*

检索是关键词加向量。只用向量，"上次那个流程"这种指代召不回来。只用关键词，换一种说法又找不到。两条都要，因为用户的话和技能的写法经常不是同一套词。

和记忆是同一条规则：目录可以很大，常驻在提示词里的只能是目录。正文按这一轮的需要再取。

工具说明是更碎的一笔。每个工具的名字、描述、参数 schema 都要进上下文，工具一多，光 schema 就上千 token。描述因此有长度上限，"为什么调用"压成一句话。省下的不是功能，是每一轮都要重复付的固定租金。

## 六、上下文是预算

几块东西抢的是同一个窗口，也是同一张账单：

| 块 | 全量时怎么爆 | 现在怎么装 |
| --- | --- | --- |
| 记忆 | 254KB 每轮都进提示词 | 按这句话取前几条 |
| 技能 | 目录几千 token | 名字加 50 字，用到再取全文 |
| 历史 | 中文尺子偏小，压缩不触发 | 按模型分词，到 85% 再压，留最近 10% |
| 工具结果 | 图片被串成文本 | 按图片 token 计 |
| 工具说明 | schema 上千 token | 描述有长度上限 |

review 里据此留了四条。

**每一块都要有配额。** 系统提示、记忆、技能、历史、工具结果，各自有上限。超了按优先级裁，不能靠"先拼进去，超了再让模型自己忍"。

**能按需就不要全量。** 全量是最省事的默认值，也是最贵的。记忆和技能都是先全量，再被账单打回来。

**能压缩就不要原文，压完还要追溯得回。** 这一条还没做到。checkpoint 里的原文收成摘要之后，没有通用的路把原话还回去。只有分享后续聊那一处，会把数据库里的历史写回恢复点（[第五篇]({{ '/agent/agent-from-0-to-1-part5/' | relative_url }})）。做不到追溯，压缩就是把细节从模型手里拿走，用户那边的账本还在，两边又对不上。

**计量用模型自己的尺子。** 字符数除以四、字数、另一个模型的分词器，都会把 85% 算成还没到。289 和 780 差的那一截，就是压缩整个月没工作的原因。

## 七、最后

254KB 烧掉的，是长事务里的"要花钱"。工作记忆有硬上限。全量注入是把档案当寄存器：档案可以无限厚，寄存器不行。

存哪儿可以再换。注入多少、什么时候注入、谁有权写，这三句决定它会不会再涨回 14 万。塞进这一轮的每一样东西，都在挤别的东西，也都在计费。

还欠着的，是只增不删、用户看不见也删不掉，以及收尾才写、下一轮才读得见。[下一篇]({{ '/agent/agent-from-0-to-1-part8/' | relative_url }})把这些和另外几个洞放在一起：**我们还没解决的五个问题。**
