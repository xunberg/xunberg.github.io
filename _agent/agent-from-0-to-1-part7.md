有用户反馈：最近变慢了。

不是慢一点。首字出来要等二十五到四十秒，桌面端和浏览器同时变慢。

我们一开始怀疑模型、怀疑网络、怀疑网关。最后定位到一个文件：254KB。

那是这个用户的长期记忆。每一轮对话，它被完整地塞进提示词。

---

## 一、我们想要的记忆，和实际发生的

做记忆的初衷很简单：记住用户的偏好、常用参数、上次的选择，别每次都重新问。

第一版都会这么写：

```python
def build_prompt(user_id):
    memory = read_file(f"memory/{user_id}.json")   # 每次全量读
    return system_prompt + memory                  # 直接拼进提示词

def after_round(user_id, messages):
    memory = read_file(f"memory/{user_id}.json")
    memory += llm.extract("这轮有什么值得记住的", messages)   # 模型自己决定写什么
    write_file(f"memory/{user_id}.json", memory)
```

读是全量，写是模型自觉。

能跑，但没人管得住它。模型很勤奋，每轮都往里写；写了不删，也没有上限。几个月后，单个用户的文件涨到 254KB——按当时的口径，每轮十几万 token，光把记忆读进去就要几十秒。

用户感受到的"变慢"，其实是我们在每一轮开头，先把一本越来越厚的日记念给模型听。

复盘时看得很清楚：这段代码错在两处——**读的时候不筛选，写的时候不设防。**

## 二、四代演进

| 代 | 做法 | 为什么换掉 |
| --- | --- | --- |
| 一 | 自定义 JSON 分桶，模型主动写 | 无界增长，写什么全凭模型自觉 |
| 二 | 换成框架原生的记忆文件，全量注入 | 更糟：文件是纯文本，膨胀得更快 |
| 三 | 出事当天关掉注入止血，改接独立记忆服务 | 先让用户能用 |
| 四 | 检索式读取 + 写入收到轮次收尾 | 现在这一代 |

第三代到第四代之间，我们砍了两刀，正好对应上面那两处：**读从全量改成按需，写从模型改成系统。**

**第一，从"全量注入"改成"按需检索"。** 每轮只拿用户的这句话去检索，命中几条就注入几条。254KB 变成最多几条记忆，十几万 token 变成几百。

读取留了两条路：一条是每轮开头用用户这句话去检索，命中就注入；另一条是模型自己调工具检索。前者保证"不用问也能想起来"，后者保证"想细看时能查"。

检索只取前几条。记忆不是文档，三五条足够影响判断，多了反而挤占上下文。

![记忆的读有两路，写只有一路]({{ '/assets/images/agent/agent-from-0-to-1/p7-01-memory-read-write.png' | relative_url }})

*图 1：读有两路（预取、工具），写只有一路（收尾）。*

**第二，把写权限从模型手里收回来。** 模型不再有"写记忆"的工具；一轮结束后，系统拿这一轮的用户消息和助手回复，交给记忆服务自己提取事实。

第二件事比第一件更重要。因为只要模型能自由写，它就会把一次性的确认、临时的参数、任务的中间状态全写进去。记忆应该是"沉淀"，不是"流水账"。

这套做法也有代价：我们目前没有遗忘机制。记忆只增不删，用户也没有入口去看和删。这是我们欠的下一个债。

## 三、一个反直觉的结论

我们一开始以为问题是"记忆存在哪"：文件还是数据库，自己写还是用现成的。

后来发现，真正的问题有三个，存哪儿反而不重要：

1. **注入多少。** 全量还是按需，这一条决定成本和延迟。
2. **什么时候注入。** 每轮开头注入，还是模型主动检索，这一条决定它会不会干扰当前任务。
3. **谁有权写。** 模型写还是系统写，这一条决定它会不会变成垃圾场。

这三条想不清楚，换什么存储都会重演。

## 四、同类的三个坑

记忆只是上下文问题的一个切面。同一个月我们还踩了三个。

**中文压缩不生效。**

框架自带的压缩中间件用"四个字符约等于一个 token"来估算。英文差不多，中文差得离谱——实测一千多个汉字，它估 289，真实是 780，低估 2.7 倍。

后果不是"压缩得不准"，是"永远不触发"：阈值按 85% 上下文算，估算值永远到不了 85%，于是一路涨到爆窗口。

后来我们换了一个按模型校准的分词器，中文按实际比例算，图片给固定成本。压缩才真正开始工作。

触发条件是上下文到 85%，保留最近 10%。这两个数字不是拍脑袋，是按模型窗口和"最近几轮必须原文"的经验定的。

**一张照片吃掉半个窗口。**

工具读图片时返回的是 base64。某个模型适配层会把工具结果序列化成字符串，base64 就从"图片"变成了"文本"——按字符计费。

一张 317KB 的照片，一次调用 30 万 token，接近窗口的六成。修好之后，同一张图大约 242 个图片 token。

差了一千多倍。这不是优化问题，是正确性问题。

**输出上限把工具参数截断了。**

有一类轮次特别长：模型先想很久，然后一次性写一个大文件。我们把单轮输出上限设成 16K，结果工具参数写到一半被截断，模型拿到一个残缺的 JSON，报错，重试，再截断。

调到 64K 之后才稳定。这类问题在短对话里永远发现不了。

## 五、技能也按需加载

上下文预算的另一个大客户是技能。

一开始我们把所有技能的说明全量注入提示词：名字、描述、用法。技能一多，光目录就几千 token，而且大部分和当前任务无关。

后来改成三层：

- 提示词里只放技能名和一句不超过 50 字的摘要，让模型知道"有什么"；
- 需要细节时，调检索工具，只返回摘要列表；
- 真正要用时，才把完整说明取出来。

这三次加载，成本从"每轮几千 token"降到"用到才付"。

![技能分三次加载，用到才付全额]({{ '/assets/images/agent/agent-from-0-to-1/p7-02-skill-layers.png' | relative_url }})

*图 2：技能的第三次加载，才付全额。*

检索用的是混合召回：关键词加向量。只用向量，用户说"上次那个流程"召不回来；只用关键词，说法一换又找不到。

## 六、上下文是预算，不是字符串

还有一个容易被忽略的支出：工具说明。每个工具的名称、描述、参数 schema 都要进上下文，工具一多，光 schema 就上千 token。所以我们给工具描述设了长度上限，也把"调用原因"压成一句话。

踩完这些，我们总结出四条，写进了 review 清单：

**第一，每一块都要有配额。** 系统提示、记忆、技能、历史、工具结果，各自有上限，超了按优先级裁。

**第二，能按需就不要全量。** 全量注入是最贵的默认值，而它往往是最省事的默认值。

**第三，能压缩就不要原文。** 前提是压完还能追溯。这一条还没做到：checkpoint 里的原文压成摘要之后没有通用的回灌，只有分享续聊那一处会把数据库历史写回恢复点（[第五篇]({{ '/agent/agent-from-0-to-1-part5/' | relative_url }})）。做不到追溯，压缩就是把细节从模型手里拿掉。

**第四，计量要用模型自己的尺子。** 字符数、字数、别的模型的分词器，都会骗你。

---

## 七、最后

254KB 那次烧掉的，是长事务里的"要花钱"。工作记忆有硬上限，全量注入是把档案当寄存器。

存哪儿不重要。注入多少、什么时候注入、谁有权写，这三条决定它会不会再涨回去。塞进这一轮的每一样东西，都在挤别的东西，也都在计费。
