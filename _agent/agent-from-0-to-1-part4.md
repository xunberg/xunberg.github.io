有一次，我们打开 API 容器的镜像看了一眼：好几个 G。

里面有整套 Agent 框架、有沙箱 SDK、有几个 G 的科学计算环境，还有一堆我们自己也说不清什么时候装上的东西。

有人问了一句：这个镜像是干什么的？

它是 API。负责鉴权、查库、转发请求。

后来我们才发现，它同时还是 Agent 的运行时——所有对话都在这个容器里跑。

---

## 一、框架自带的运行时，假设了什么

DeerFlow 自带一个图执行服务：负责建图、执行、存 checkpoint、往前端推 SSE，外面再套一个 gateway 做鉴权和转发。

这套结构在 demo 里很顺，因为它默认了三件事：

1. 一次会话，对应一条 SSE 连接；
2. 状态，存在框架的 checkpointer 里；
3. 执行就在这个进程里——进程活着，会话就活着。

这三条在"一个人、一个浏览器、不刷新"的场景下都成立。

对外测试开始之后，三条挨个碎了。

用户刷新页面，连接断了，事件就丢了。服务重启，正在跑的那一轮没了。想加个副本，发现 SSE 的订阅状态在进程内存里，加不了。

最难受的是，这些都不是偶发故障，而是结构的必然结果：只要连接、执行、状态三样东西绑在同一个进程里，任何一次重启、任何一次扩容，都会把它们一起带走。

不是框架写得差，是它的扩展单位和我们不一样：**它的单位是"一个进程"，我们的单位是"一轮对话"。**

说清楚这笔交换：框架原本把跑图、恢复点、推流绑在一个进程里。拆完之后，跑图还在框架里，但只留在执行层；事实进数据库，在途事件进队列，恢复点仍是 checkpoint，接入层不再读它。**省下的是耦合，欠下的是实现**——三份写入要自己维持，而且它们之间没有事务。

---

## 二、第一次尝试：把 Agent 搬进 API 进程

我们的第一反应很朴素：既然框架的运行时不好用，那就别用它，直接把 agent 搬进 gateway 里跑。

于是 submit 路由里直接跑起了 astream。

结果换了一种疼：

一个 API 请求要挂三分钟；改一句提示词要重启 API；agent 一崩，整个 API 跟着崩；并发一上来，API 的连接全被 agent 占着。

这个阶段其实很舒服：一个进程，断点能一路跟下去，本地起一个容器就能调。

舒服的代价是：API 的可用性和这一轮执行的可用性绑在一起。提示词、沙箱、模型，任何一处把进程打满，鉴权和开单一起不可用。

这时候我们才想明白：问题不是"agent 该放在哪"，是"一个进程该干几件事"。

## 三、真正的拆法：两层

最后的分工是这样：

![接入层与执行层拆分后的开单与回放]({{ '/assets/images/agent/agent-from-0-to-1/p4-01-runtime-split.png' | relative_url }})

*图 1：两层 + 三个契约。接入层只碰 HTTP、数据库和队列，不碰 agent 内部。*

中间只留三样东西：Redis 负责排队和传输，数据库负责事实，一个很小的任务协议负责派发。

整个拆分里最关键的一步，是**让 submit 不再返回内容，只返回"已开单"**。

内容一律从 resume 拿。当时看着很绕，但它一次解决了三件事：断线重连、多端同看、刷新恢复。因为这三件事本质上是同一件事——"把正在发生的事，从连接里解耦出来"。

**顺序比方案重要。** 我们做对的一件事，是先把契约定下来，再搬代码：第一步只做协议层，把任务参数变成纯 JSON、定好信封，让两边都能解析，执行还留在原地；第二步才把执行搬过去；第三步才拆依赖、拆镜像。

如果反过来，先搬代码再想协议，两边会长期处在"一半在新家、一半在旧家"的状态，任何一次发布都可能踩空。

我们也认真评估过：能不能继续用框架自带的图执行服务？

它能跑图，也能存 checkpoint。但它的扩展单位是"进程"，不是"任务"；它不知道什么叫一轮对话、什么叫积分、什么叫用户刷新页面。要在它上面补齐这些，等于在框架里再写一套业务运行时。

所以最后的选择不是"用不用框架"，而是"框架管到哪一层"。

## 四、拆的时候，最难的三个东西

**第一，状态。**

接入层以前要读 checkpointer 才能做恢复和中断。拆完就不能读了——那是个框架私有的完整 blob，动辄几 MB，还没有任何查询能力。

于是中断改成"置一个 Redis 标志，让执行层自己看"，历史改成"只从数据库读"。这两处改动看着小，实际把接入层对 agent 运行时的依赖整个切断了。

**第二，协议。**

任务里只能传纯 JSON。像中断恢复指令这种框架运行时对象，不能出接入层。

我们最后定了一个信封：`{biz_key, payload, trace_id}`。`biz_key` 是任务类型，`payload` 是纯数据，`trace_id` 用来把两个进程的日志串起来。

顺带踩了一个坑：任务 id 直接用轮次 id。好处是天然幂等——重复提交会被队列静默丢掉；坏处是"想重跑同一轮"必须换 id，否则你以为发出去了，其实什么都没发生。

**第三，依赖。**

目录拆了，pip 还混着——这是最典型的假拆分。

我们的验收方式不是看目录，是看 import：

- API 镜像里，web 框架必须 import 成功，agent 框架必须 import 失败；
- 执行层镜像反过来。

这条命令比任何架构图都管用。因为"目录拆开、依赖没拆"这件事，只有运行时才知道。

回到开头那个问题：API 镜像里为什么会有科学计算环境？

因为有个本地执行后端要用它。它跟 HTTP 一点关系都没有，但因为它和 agent 跑在同一个容器里，就被一起打包了。拆依赖之后，它跟着 agent 去了执行层，API 镜像瘦了一大圈。

---

## 五、拆完之后的代价

拆得干净，代价也是真的。

**两条路径必须同构。** 实时推的和回放给的，格式一旦不一致，前端就会"刷新丢内容"。这个坑我们踩过——数据一条没少，用户看到的是残缺的。

**调试变成跨进程。** 一次 submit 的日志现在分散在两个容器里，没有同一个 trace id 根本对不起来。我们后来给每个请求打了同一个 id，一次提交在接入层十几行、执行层三十行日志里能串起来。

**部署变复杂。** 从 1 个服务变 2 个，本地开发也要起两个，发布要保证两边版本兼容。

**跨进程才会出现的 bug。** 比如队列名在模块加载时从环境变量读，两边各读了一份不同的默认值，消息进了没人消费的队列。这种 bug 单进程里不存在，单测也测不出来，只有把两个进程真的连起来跑一遍才会暴露。

## 六、现在长什么样

| | 拆之前 | 拆之后 |
| --- | --- | --- |
| API 镜像 | 含 agent 栈、科学计算环境 | 只有 FastAPI 和 DB/Redis 客户端 |
| 一次 submit | 在 API 进程里跑几分钟 | 只做鉴权和入队，执行在别处 |
| 改提示词 | 重启 API | 只重启执行层 |
| 扩副本 | SSE 状态在本地，扩不了 | 两层各自扩 |

一句话总结这张表：**框架只负责"怎么建图"，不负责"这一轮到底发生了什么"。**

分工可以写得很具体：

接入层留下鉴权、配额、开单、回放、WebSocket 中继——所有"跟人打交道"的事。

执行层拿走建图、工具、沙箱、收尾——所有"跟模型和机器打交道"的事。

判断标准只有一条：**这件事需不需要知道 agent 内部长什么样。** 需要，就去执行层；不需要，就留在接入层。

拆开之后还有个好处：两层可以按不同指标扩容。接入层是 IO 密集，看连接数；执行层是 CPU 和 token 密集，看队列长度。绑在一起的时候，只能按最贵的那个扩。

## 七、最后

拆运行时拿回来的，是长事务里框架不知道的三件事：

- **谁在跑这一轮**：排队、并发、排队期间队列没了怎么办；
- **这一轮怎么结束**：进程死了怎么写成终态，不能让用户看见一条永远"运行中"的会话；
- **断了从哪看**：事实从数据库回放，在途从队列续上，两边形状必须相同。

框架做不好这三件，是因为它的单位是进程。它不知道什么叫一轮，不知道费用记在哪，也不知道用户刷新时期望看到的是同一份过程。

我们后来分别用三种机制去解：队列加心跳管"谁在跑"，四态收尾管"怎么结束"，数据库加回放管"从哪看"。

这三件里最难的是第三件。下一篇，我们就聊它：**状态到底该放在哪。**
