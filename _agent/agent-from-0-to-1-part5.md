有一次，用户刷新页面之后，历史全在。

但他接着问了一句"刚才那个参数是多少"，模型答不上来。

我们查了半天，最后确认：它确实忘了。用户看到的那份历史，和模型手里的那份，从来不是同一份数据。

## 一、系统里其实有三份记忆

| 谁在看 | 存在哪 | 完不完整 | 活多久 |
| --- | --- | --- | --- |
| 用户、审计 | 数据库，一条条消息 | 完整，只追加 | 永久 |
| 模型 | 框架的 checkpoint | 可能被压缩、被裁剪 | 一轮到一次中断 |
| 正在看屏幕的人 | Redis 队列 | 只覆盖当前这一轮 | 一小时 |

同一句话，在三处是三种形态：数据库里是一条记录，checkpoint 里是图状态的一部分，队列里是一串 chunk。

这三份是三种读者：人、模型、正在看屏幕的连接。加上沙箱里的文件，才是四种职责——事实、传输、恢复点、执行现场。沙箱不是记忆，它是代码改过的世界。读者有三个，职责有四个。合成一份，后面两种故障都会出现：人看见的历史还在，模型已经忘了；或者恢复点被拿去当账本，既查不了，也慢。

写入的时机也不一样：用户消息在提交时写；模型的回复和工具结果在流式过程中逐条写；轮次的指标和积分在收尾时写；checkpoint 则是图每走一步写一次。四套写入，四个触发点。

## 二、为什么不能只用一份

第一版想得很简单：checkpoint 里本来就有完整历史，断线重连直接读它就行。

```python
async def resume(thread_id):
    state = await checkpointer.aget(thread_id)   # 整份快照
    for msg in state["messages"]:
        yield sse(msg)
```

三个问题，一个比一个硬：

- 它可能已经被压缩。读出来的历史和用户看到的不一样——开头那个"模型忘了"，就是这一层。
- 它是框架私有格式的完整 blob，不可查、不可审计、不可计费，而且长对话读一次很贵。我们测到过，收尾时同步序列化一次，能把新任务排队拖到 P90 55 秒。
- 正在跑的那一轮不在里面。图还没走到下一步，刷新就什么都看不到。

那换数据库？每一轮都要把全量历史重新灌给模型，成本高；而且图内的短期状态——待办、中断点、工具调用的中间态——没法存。

只用队列？连接一断就没了。

所以只能分。分的代价是：**这几次写入之间没有事务。** 数据库写成功了，checkpoint 可能没写；反过来也一样。长事务的提交点在收尾，不在中途这四次写入上。中途死掉，靠补偿把终态写圆，不靠跨库回滚。这个代价我们认了。合成一份的代价是系统扩不了，而且账和恢复点会一起坏。

## 三、断线重连是怎么做的

先说结论：**submit 只"开单"，内容一律从 resume 拿。**

- submit 做三件事：分配轮次、注册队列、把任务入队。响应里没有内容。
- resume 带一个 `offset`，意思是"我已经看到第几轮了"。
- 服务端比较 `offset` 和当前活跃轮次：落后了就先把历史从数据库补上，再从队列拿实时的。
- 最后一条 `end` 事件里带 `total_rounds`，客户端下次就拿它当 `offset`。

这里有个关键设计：**队列是广播的，永不消费。** 每个读的人自己记位置。

队列本身有一小时的存活时间，每写一次续一次；轮次结束后延迟清理，给还在读的客户端留出时间。

所以多端同看、反复刷新、断线重连，用的是同一套机制——它们本质上是同一件事：把"正在发生的事"从一条连接里解耦出来。

但也是这里埋了一个坑：历史回放是"消息级"的，实时流是"chunk 级"的。格式一旦不一致，前端就会出现"刷新丢内容"——数据一条没少，用户看到的是残缺的。

历史能只追加，靠的是消息 id 不是随机生成的。我们用它所属的会话、轮次和来源算出一个稳定的 id，同一条消息被写两次、被中途补齐一次，落的都是同一行。序号则由数据库里的一把事务锁串行分配——并发写撞唯一键，是早期整条消息丢失的主要原因。

顺便说一个我们改过的决定：历史回放以前也读 checkpoint，后来全改成只读数据库。原因有两个——checkpoint 是完整 blob，读一次很贵；而且它可能被压缩，读出来的历史和用户看到的对不上。数据库慢一点，但它是同一份事实。

## 四、假死：进程死了，状态还活着

用户看到的"卡住"，很大一部分不是慢，是**执行的人已经不在了**。

worker 被 kill、容器被驱逐、发布重启——正在跑的那一轮收尾没执行，会话状态就永远停在"运行中"。前端一直转圈，后台没有任何进程在干活。

我们的解法是心跳加巡检：

- 每轮开始时种一个心跳 key，长 TTL，覆盖"已入队但还没被 worker 领走"的空档；
- worker 执行期间改成短 TTL，定期续期；
- 这轮正常结束、抛异常、被取消，都要把 key 删掉；
- 网关侧常驻一个巡检，扫"运行中但心跳已消失"的会话，条件更新成异常。

实测：在调紧的配置下（心跳 15 秒、巡检 5 秒），硬杀进程 18 秒判死，优雅停止但没跑完 26 秒判死。生产配置宽松得多——心跳 90 秒、巡检 30 秒、宽限 3 分钟，判死是分钟级。

按设计，正常执行中的轮次不会被误杀。

有个细节值得记：**巡检必须放在网关，不能放在 worker。** 因为 worker 里的循环会跟着 worker 一起死，自己看不住自己。

但设计归设计。这套机制真的误杀过一次：某天两个正在输出的线程同时被判死，用户看到内容突然中断。

根因是"活跃轮次"那个映射 key 只在建队时设了一次过期时间，长轮次跑到一半 key 就过期了，巡检据此认定"已经没有进程在跑"。

修复是两件事：把需要续期的 key 统一登记，由心跳同频续；巡检在 key 丢失时，先反查最近落库的消息属于哪一轮，再决定。

## 五、恢复的五条路径

| 场景 | 靠什么恢复 |
| --- | --- |
| 断线、刷新、多端 | 数据库回放 + 队列重放 |
| 崩溃后继续聊 | 下一轮从 checkpoint 接着跑 |
| 中断后等用户回答 | checkpoint 里的中断点 + 恢复指令 |
| 假死回收 | 巡检置异常 + 补一条错误记录，让前端重放错误事件 |
| 分享后继续聊 | 把数据库里的历史反向灌回 checkpoint |

最后一条值得单独说：分享续聊是唯一一处**主动把数据库历史写回 checkpoint** 的代码。它证明这件事是可行的——只是我们没把它做成通用能力。

## 六、三个还没补上的洞

**第一，checkpoint 丢了没法重建。**

用的是内存版 checkpointer 的时候，或者 checkpoint 表被清了，模型会"失忆"，但界面上的历史还是完整的。这是最难排查的一类故障：一切看起来正常，只有模型变笨了。

**第二，三份之间没有事务。**

进程恰好在"数据库写完了、状态还没改"之间死掉，就会留下不一致。我们有补偿（补落盘、错误记录），但没有事务。

**第三，压缩不可逆。**

checkpoint 里的历史被压缩成摘要之后，原文只在数据库里躺着。模型再也看不到细节，也没有"把原文还给它"的路径。

---

## 七、最后

一句话记住这一篇：**checkpoint 是"给模型看的记忆"，不是"事实"。**

事实在数据库里。传输在队列里。资产在沙箱里。短期状态才在 checkpoint 里。

把这四样东西混成一样，系统在 demo 里会更简单，在生产里会到处漏。
