有个会话，每一轮都失败，失败原因都一样。

用户重试了七次，我们重启了两次服务，它还在失败。

最后查出来：上一轮被取消的时候，留下了一次没有结果的工具调用。下一轮开始，修复逻辑把整段历史重写了一遍；再下一轮，又重写一遍。每修一次，就多留下一个错误形态，模型每次都撞在同一个地方。

这不是"一个 bug 修了七次"，是"一个 bug 每轮都会重新长出来"。

---

## 一、一轮对话有四种死法

| 死法 | 谁触发 | 用户看到什么 |
| --- | --- | --- |
| 正常完成 | 模型自己结束 | 结果 + 耗时 + 积分 |
| 用户中断 | 点"停止" | 已经流出的内容 + 一个中断标记 |
| 外部取消 | 超时、重启、关停 | 同样的内容 + 一条"服务异常" |
| 执行异常 | 模型、工具、沙箱报错 | 一条错误事件，能重试 |

这四种是不等人的结束。等人是另一种终态：工具成功，这一轮提交成"等待"，回答算下一轮（[第二篇]({{ '/agent/agent-from-0-to-1-part2/' | relative_url }})）。下面说的是等待之外，一轮怎样停下来。

看着像四种收尾，其实是**四套不同的结束语义**，成功也在里面。正常完成同样要提交：不写指标、不发终止、不清理队列，客户端就不知道这轮已经结束。

第一版就是在每个能结束的地方各写一段：

```python
try:
    await stream()
    await write_metrics()
    await notify()
    await mark_complete()          # 只有正常路径走到这
except CancelledError:
    await notify()                 # 忘了 mark_complete
except Exception:
    await mark_error()             # 忘了清理队列
```

结果就是：顺序不一致、漏步骤、某条路径忘了发终止事件。用户那边表现为"有时候能停，有时候转圈"。

## 二、收敛成一个入口

后来我们把收尾拆成三个可复用的单元：

- **补落盘**：把已经流出来、但还没写进数据库的内容补上；
- **成功定稿**：通知、终止事件、标记完成、清理队列；
- **失败定稿**：写错误记录、置异常、通知、延迟清理。

然后四个状态就是用这三个单元拼出来的：

![四种死法，一个出口]({{ '/assets/images/agent/agent-from-0-to-1/p6-01-four-exits.png' | relative_url }})

*图 1：四种死法，一个出口。三个单元拼出四种收尾。*

所有路径最后都调同一个函数。这一条约束带来的收益，比任何单个修复都大：**新增一种结束方式，不用改调用方。**

外部取消里最常见的是超时。我们一开始把单轮上限设成 1 小时，结果实测有 61 分钟的长轮次被硬杀——用户等到最后，什么都没拿到。后来调到 2 小时。

顺序也不能随便换。"标记完成"必须在写指标之后——否则客户端拿到完成信号立刻重连，会读到还没写完的指标；"清理队列"必须延迟——因为客户端可能还在读。

## 三、五个真实故障

**第一，悬空工具调用会每轮复发。**

用户打断或者直接发新消息时，checkpoint 里会留下一次"模型调了工具、但没有结果"的调用。图上不允许这种悬空，所以必须有地方补一条占位。

我们最早的修法是收尾时重写整段历史。看起来很干净，但整段历史会重新流经消息流——特殊工具的结果被当成新消息又下发一遍，前端就反复弹同一个确认框（[第二篇]({{ '/agent/agent-from-0-to-1-part2/' | relative_url }})里提过）。

后来改成反方向：不动历史，只在下一轮开头，在尾部补一条占位。历史是只追加的，这个约束一旦破，就会出现两个版本的真相。

**第二，并发写消息会撞唯一键。**

消息落库是异步回调，收尾时还会补写。两处并发时各自算"当前最大序号 + 1"，撞上唯一键，整条消息就丢了。

修复是给同一个会话的序号分配加一把数据库事务级锁，串行化。代价是同一会话的消息写入变成串行——但消息本来就是顺序的，这个代价可以接受。

顺带说一个反直觉的决定：任务队列的重试次数设成了 1，也就是不重试。

因为一轮执行的副作用——消息、积分、记忆——重跑会再做一遍。回放可以重复，那是把已经发生的记录再读给人和前端；执行不能重试，那是再产生一次副作用。宁可让这一轮失败，由收尾和巡检把终态写清楚。两个执行者还会互踩心跳、重复收尾。

**第三，终止事件可能永远发不出去。**

收尾要做很多事：写指标、写积分、写记忆、通知前端。只要前面任何一步抛异常，后面的"标记完成"就被跳过了。

而客户端的逻辑是"等到完成标记才结束"。所以表现就是：内容都收到了，界面还在转圈。

修复很土：把"标记完成"放进 finally。顺序上它必须在指标和积分之后（要带上最终值），但无论前面成不成功，它都必须执行。

**第四，假死回收之后，客户端以为一切正常。**

进程被 kill，巡检把状态置成异常。但历史回放时没有任何错误记录，客户端看到的就是"这一轮正常结束了，只是没有内容"。

修复是补一条错误记录，让回放在同一位置重放一条错误事件——和 worker 自己失败时走同一个出口。

**第五，队列被替换了，旧轮还在跑。**

同一个会话发了新消息，旧轮的队列会被删掉。但旧轮的 worker 不知道，继续跑，继续往一个不存在的队列里写 chunk。

结果是：白烧模型的钱，日志里刷满"队列不存在"。

修复是加一个看门狗：每秒钟看一眼队列还在不在，不在就硬取消。同时，任务在真正开始执行前也检查一次队列——已经没了就直接跳过，连图都不用建。

## 四、三条不变量

走到今天，可靠性这块我们只守三条：

1. **收尾只有一个入口。** 任何结束路径都必须经过它，不允许在别处补状态。
2. **结束信号放在 finally。** 它可以是最后一步，但不能是"成功才执行"的一步。
3. **错误必须落库，并且能被重放。** 用户刷新之后看到的历史，要和当时看到的一样，包括失败。

第三条最容易被忽略。我们一度觉得"错误是运行时的事，历史只存内容"——结果就是刷新之后，一次失败看起来像一次正常结束。

还有一个配套：错误码。每个错误都被归类成一个稳定的 code 加一句本地化文案，原始异常只进日志。这样前端能按 code 做不同的引导——重试、换模型、检查沙箱——而不是统一弹一句"服务异常"。

---

## 五、一百三十多个 fix 换来的是出口

最近两个多月，一百三十多个提交是修 bug。修之前，这些失败多数没有终态：进程被杀，会话一直转圈；并发写丢一条消息，看起来像模型没回。现在失败会在分钟级里写成异常，并且能被回放。

可靠性不是没有 bug。是每种结束都经过同一个提交点，失败和成功一样能被人看见。

---

## 六、最后

这一篇补的是长事务里的"会失败"：失败要落成明确的终态，收尾就是提交点。

成功、用户中断、外部取消、执行异常，四种走同一个函数。请求失败了，返回错误就结束。这一轮失败了，还得让人看见失败在哪一步、已经做了什么、能不能接着来。
