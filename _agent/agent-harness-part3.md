两个工单，先后到的。

第一个：某个会话每一轮都失败，失败原因一模一样。用户重试了七次，我们重启了两次服务，它还在失败。

第二个：工具调用的参数偶发是坏的。JSON 缺一半、两个调用的参数串在一起、有的调用直接消失，占比千分之几。换一台机器、换一个时间，复现不出来。

两单都出在 tool_call 上，根因不是一类。第一单是一条闭合的数据回路：错误的占位写在 checkpoint 里，下一轮把它读出来，再写一条新的。重启换掉的是进程，换不掉那条消息。第二单是流式传输的时序，以及思维链和正式输出共用的 token 额度。相关代码在自己的单测里是对的。

它们还落在第二篇留下的两道边界上。配对完整，是给模型看的约束，记在 checkpoint 里。人看见的历史记在消息表里。还在传输的半成品记在只追加的日志里。补丁如果写错了存储，或者一段还没拼完的参数写进了日志，模型和人会读到两份对不上的记录。这篇从这条约束推：配对在什么时机补，补成什么形态，写进哪一份存储。

## 一、配对是一条不变量

工具调用协议要求有界配对。模型一条响应里出现过的每个 tool_call，下一次请求的历史里必须有恰好一个对应结果。多一个、少一个、次序错了，模型 API 直接拒绝这次请求。没有降级，也没有"忽略这一条接着聊"。

合法的最小形状是这样：

```text
assistant:
  tool_calls: [ { id, name, arguments } ]
tool:
  tool_call_id = 上面那个 id
  content      = 工具的结果
```

`tool_call_id` 对不上，或者 assistant 后面直接接了用户的下一句话，这份历史就不能再发给模型。

执行保证不了这个形状。一轮里模型可以一次发出一批调用。框架逐个跑工具、逐个回填结果，整批提交进 checkpoint，然后才进入下一次模型调用。提交之前有一个窗口：**调用已经写进当前消息，结果还没回来，checkpoint 还没落定。** 用户点停止、用户直接发新消息把这一轮换掉、进程被杀，都经常落在这个窗口里。留下的记录是同一种：checkpoint 里一条带 `tool_calls` 的模型消息，没有任何工具结果跟它配对。下面把这种记录叫做未配对调用。

下一轮一开始，框架把这份历史发给模型 API，请求被拒。所以必须有人把配对补上。能选的只有两件事：在什么时机补，补成什么形态。时机和形态错了，补上去的那条消息会变成下一轮的输入。第一单就是这条路。第二单更早：参数在变成一个完整 tool_call 之前就已经缺了一段，后面无从配对。

> **模型决定调什么。夹具保证这一来一回在协议上始终成对。** 这是 harness 要守的不变量，单个业务工具守不住。

## 二、修复的输出，成了下一轮的输入

### 未配对调用是怎么留下的

取消发生在工具执行的中途。编排面写一个取消标志，执行面在循环间隙看见它，硬取消当前这轮。流停在半截：模型消息是完整的，`tool_calls` 都在，工具结果一个都没回。

此时历史有两个读者，要求相反。

模型 API 要求配对完整，否则下一轮请求发不出去。人要求账本只追加，而且只追加真正发生过的事。{{ '/agent/agent-harness-part2/' | relative_url }}是：消息表一旦被改写，回放、审计、记忆就不知道以哪一版为准。

第一版修复只满足了模型，而且选在这一轮最不一致的时刻：取消收尾。检测到未配对调用，就把整段历史重写一遍，删掉尾部，合成一批占位 ToolMessage，同步写进消息表。按协议，下一轮能发出去了。按账本，这一轮被删掉之后又写了一份新的。

### 占位被读成待答卡片，收尾再写一次

占位按通用结构合成，内容是一段纯文本。我们的等人工具——表单、选择题——挂起时，checkpoint 里也是一条 ToolMessage，只是它的内容必须能按卡片协议解析。恢复逻辑分不清这两条。它扫到占位，就按待回答的卡片去读：

```python
card = json.loads(tool_message.content)  # 占位是纯文本，这里抛异常
```

整轮因此以异常结束。异常结束和取消结束走同一条收尾。收尾里的修复再跑一遍，再写一条错误占位。下一轮继续失败。

![修复输出成为下一轮输入]({{ '/assets/images/agent/agent-harness/03-repair-loop.png' | relative_url }})

*图 1：修复写出的占位，就是下一次修复要读的输入。重启换的是进程，checkpoint 里那条占位还在。*

回路闭合在两步之间：异常结束，以及收尾再写一条占位。用户重试七次，是把这张图跑了七圈。我们重启两次服务，换的是执行进程。checkpoint 里的占位还在，恢复逻辑仍会去解析它。

> **在结束时改历史的方案，会在异常结束时再运行一次。** 判断一个修复会不会让下一轮重复失败，就看它写出去的记录，会不会成为它下一次运行的输入。

取消瞬间还有一个更早的原因：那一刻的状态还没对齐。流停在一半，checkpoint 可能没提交，消息表和队列里的轮次状态可能还不一致。在这个时刻改历史，改的是一份还不能当依据的快照。

### 配对改到下一轮开始、调用模型之前

新方案先定三条。时机、语义、写入哪一份存储，各管一件。

**取消时刻不补配对。** 取消收尾只做两件事：把已经流出来的内容补进消息表，把会话状态置为中断。历史不改。未配对的 tool_call 留在 checkpoint 里。此刻没有人要拿它做下一次模型调用，所以不必在状态还没对齐时补。

下一轮开始时，上一轮的收尾已经结束，该落的库落了。这时再重放尾部，在用户的新消息**之前**插入配对的 ToolMessage。这一步的输入是已经稳定的历史。账本只往后追加，不出现第二个版本。

**等人工具用用户的新消息当回答，其他工具记成失败。** 模型弹着表单问"用哪个参数"，用户没填，点了停止，然后打了一句"用默认的"。

若一律补 `status=error`，协议上成对了，这句话没有字段可放。卡片显示已失败，用户的回答留在卡片外面。界面上像那轮交互没发生过。

等人工具有自己的恢复解析：把用户这条新消息填进卡片，产出的形态和"正常挂起之后用户回答了"相同。模型看见的是"我问过，用户说用默认的"。用户看见的卡片是已回答。命令执行、文件读写没有这个语义，它们确实没有完成，就合成 `status=error`。编一个成功结果，会让模型以为工具跑完了。

没有注册恢复语义的工具，默认走 error。少注册一种，那种工具的调用会再次失去配对。默认失败至少让协议先成立。

**占位只进 checkpoint，不进消息表。** checkpoint 的读者是协议，它需要那条配对，否则请求发不出去。消息表的读者是人，回放里不该出现一条界面上从未展示过的失败。回放碰到 `status=error` 的占位就跳过。同一个事实——这轮有个工具没跑完——协议需要这条记录存在，人不需要它出现在账本上。这是第二篇"存储由读者决定"用在行动协议上的一次。

修完之后，被中断的会话能接着跑，这种每轮重复的失败没有再出现。上线前补了近四百行端到端回归，覆盖四条路径：普通中断后续跑、等人工具中断后用新消息回答、连续中断、中断后立刻发新消息。

这个 bug 没有单元测试可写。中断信号、checkpoint 的提交窗口、恢复解析、消息表，每一段单独看都是对的。重复失败出现在四段接在一起的时候。从这以后，修这种跨边界故障的提交要带端到端回归。单元测试证明每一段是对的，端到端证明接在一起之后，修复不会再把下一轮写坏。

## 三、参数残缺：同一种症状，两个根因

第二张工单的症状是参数偶发残缺。追下去是两条独立的链，都发生在 tool_call 从模型流到前端之前。收集器解决了第一条。第一条消失之后，第二条才显出来：参数不是拼错了，是模型没把后半段生成出来。

### 流式协议没有"这个调用结束了"

参数是一段 JSON，在流式接口里按 token 增量到达。协议没有"此调用到此结束"的标记。分片靠空的 id 表示"我属于上一个 tool_call"，靠 name 字段的有无区分"新调用开始"和"旧调用还在继续"。各家模型在这两条惯例上的实现并不一样。

我们一开始逐个 chunk 处理，立刻向前端发出 tool_call 事件。也就是把还没拼完的参数写进[第二篇]({{ '/agent/agent-harness-part2/' | relative_url }})那条只追加的传输日志。日志不因为被读过而删除。半截 JSON 会留在这一轮里，后面每个读者都把它当成已经发生的事实。

后面是六个补丁。每个补丁都在"当前这个 chunk"里做判断，每个判断都让下一种到达顺序出错。

| 补丁 | 当时的局部判断 | 它修好的 | 下一种顺序为什么又错 |
| --- | --- | --- | --- |
| 1 | `not args` 表示"没有参数" | 改成 `args is None`。空 dict 是合法参数，不再被整条丢掉 | 名字先到、参数未到时，聚合中的 args 本来就是空 dict |
| 2 | 空 dict 也跳过，先别发 | 中途的空 dict 不再误发 | 发出之后，累积器还留着上一个调用 |
| 3 | 发出后清空累积器 | id 为空的后续分片不再并进上一个调用，两个调用不再串参数 | 参数刚拼成非空 dict 就发，后面的分片还在追加同一段 JSON |
| 4 | 推迟到本轮 chunk 序列结束再发 | 前端不再拿到半截 JSON | 判断仍写在单个 chunk 上，新的边界从别的到达顺序里出现 |
| 5–6 | 继续为新出现的情况打补丁 | 各修一种顺序 | 同一种错误换一个分片位置再出现 |

第六个补丁之后我们停手。一个 tool_call 算不算完整，取决于整条流：只有这轮 chunk 序列结束，或者下一个带 id 的调用开始，前一个调用才算收完。站在单个 chunk 上，这个问题没有答案。继续打补丁，只是把错误从一种到达顺序挪到另一种。

> **同一个 bug 的第三个补丁出现时，停止打补丁，换判定所在的层级。** 前两个可能是边界没看全。第三个说明判断放在了错误的粒度上。

机制是一个流式收集器。分片按调用 id 分桶，空 id 的分片归入当前桶，arguments 只累积、不向外发。整轮 chunk 序列结束、每个调用都拼完之后，再一次发出。完整性的判定从"这个 chunk"换成"这条流"。前六个补丁里的情况同时失去了发生条件：没有中途发出，就没有空 dict 误发，没有残留条目，没有半截 JSON 进日志。

收集器保证的是"分片到齐了才出去"。它不保证"模型把分片生成完了"。

### 截断：思维链和输出共用一个额度

收集器上线之后，参数残缺少了一个数量级，没有消失。剩下的样本不一样：JSON 从某个字节起后面没有了。不是丢了中间某一片，也不是串到了别的调用上。网络、解析、聚合都查过，都是完整的。断点在模型停止生成的地方。

根因在额度。模型开了思维链，思维链和正式输出共用同一个 `max_tokens`。当时单轮上限是 16384。一个轮次要同时满足两件事才会超出：思考很长，模型在思维链里来回推演；同时又要写一个很大的文件，文件正文也算输出 token，而且它在工具参数的 JSON 里面。思维链用掉大部分额度，剩下的写不完这段参数，输出流在 JSON 中间停住。收集器把已经生成的前半段拼完，然后发出。收集器没有丢数据。数据在生成时就停了。

几个月对不上，是因为两个条件要同时出现。长思考单独出现过，大文件单独出现过。样本里每一维都见过，两维同时出现的那些轮次没有被单独看过。偶发故障难查，常常是因为要好几个条件凑在一起，已经看到的样本每一维都在额度内。

修复是一行配置：`max_tokens` 从 16384 提到 65536。提交里更有用的是那几行原因注释：思维链和输出共享这个上限，什么样的轮次会打满，为什么是这个数。约束还在的时候，注释比那一行配置留得更久。后来改额度的人不用把这次排查再做一遍。

### 先分型，再修

两单的表面都是"参数是坏的"。修之前先分开，否则会用收集器去处理生成截断，或者用加大额度去处理分片顺序。

| | 收集器解决的（分片顺序） | 额度解决的（生成截断） |
| --- | --- | --- |
| 数据长什么样 | 丢失、错位、两个调用串参数、半截就发出去 | 从某一个字节起，后面没有了 |
| 怎么复现 | 换一种流式分片方式就能稳定打出来 | 要"长思考"和"大输出"同时发生 |
| 跟什么相关 | 模型供应商的流式实现 | 这一轮的输出体积 |
| 改哪里 | 把"是否完整"的判断放到流结束 | 改额度，或把思维链和输出分开计量 |

> **偶发故障，先找共享的、有上限的资源。** 连接池、限流配额、token 额度、序号空间。额度被用完，先于"偶尔才会出现、原因不明"。

## 四、深潜：一次中断之后，下一轮开始的那一段

把上面的修复放进同一次过程。模型弹着表单问参数，工具还在跑，用户点了停止，然后发了一句"用默认的"。

<div class="diagram-scroll" markdown="0">
<img src="{{ '/assets/images/agent/agent-harness/03-resume-pairing.png' | relative_url }}" alt="中断后下一轮开头补配对" style="width:1247px" />
</div>

*图 2：配对发生在新轮次的开头，发生在调用模型之前。取消时，消息表只补已经流出来的内容。*

**中断。** 编排面只写标志。执行面自己取消。这一步沿用[第二篇]({{ '/agent/agent-harness-part2/' | relative_url }})的分工：中断是控制面动作，执行面看见标志之后自己停。它在循环间隙检查这个标志。流停住时，模型消息已经完整，工具结果还没有。

**收尾不补配对。** 补落盘，置中断。不重写历史，不合成占位。未配对调用留在 checkpoint 里，等到下一轮开始、状态已经对齐再补。

**新轮次先扫尾部，再调用模型。** worker 从 checkpoint 恢复。恢复之后的第一步是一个钩子，在调用模型之前运行。它从上一轮结束之后的消息扫起，重放这一段，收集仍然没有结果的 tool_call。

**按工具的语义分开补。** 未配对的是等人工具：把"用默认的"交给这个工具自己的恢复解析，得到一张已回答的卡片，形状与正常挂起后的回答一致。未配对的是别的工具：合成 `status=error`，插在同一位置，只写 checkpoint。回放读消息表，这条占位不在里面。

**插入点在用户消息之前。** 模型看到的顺序必须是：我调用了工具，工具有了结果（结果可以是失败，也可以是用户的回答），然后用户又说了话。配对若插在用户消息后面，顺序变成用户先说话、工具后结束。模型会按这个错误顺序继续推理。配对要补上，还要补在原因和结果仍然成立的位置。

**发请求前再查一次。** 开头的扫描是主修复。发模型请求之前再查一次历史：仍有未配对调用，就地补上。这一层不是把主修复再写一遍。它盖住主修复没扫到的情况：以后新加的工具类型、库里已经存在的旧记录、扫描时没认出来的尾部。两层失败的方式不一样，所以叠在一起才有用。

这一轮模型收到的历史是成对的，等人工具上带的是用户的原话。用户那边，中断前的表单显示为已回答。那轮交互还在，只是从"等你填"变成了"你后来用一句话答了"。

## 五、代价与未解决的问题

**每一轮开始都要扫尾部。** 没有未配对调用的会话扫一眼就过。这个钩子的复杂度等于所有等人工具的恢复解析之和。每加一种会挂起等人的工具，就要实现并测试它的恢复解析，还要注册进去。没注册的走 error。这条默认是为了不让新工具再次留下未配对调用。

**error 占位对模型是额外的失败记录。** 经常被中断的会话，checkpoint 里会积累多条 `status=error`。协议需要它们，否则下次请求发不出去。模型读到的是"我失败过很多次"。这会不会让它后面变得过分谨慎，我们没有测量。这是协议要求留下的记录，对模型行为的影响还没量化。

**收集器把事件推迟到流的末尾。** "是否完整"放在整条流上判断，tool_call 事件就比逐个 chunk 发出要晚。前端看到"正在调用工具"的时机整体后移。工具名的片段会先到，用来填这个空档。完整和及时确实不能同时最大化。收集器选的是：写进日志的参数必须是一整段。

**65536 是提高额度，不是把预算拆开。** 思维链再长一截，写入再大一截，输出仍会在参数中间停住。结构性的做法是思维链和正式输出分开计量，或者超出上限时分段把参数续完。我们知道这条路，没有做。现在的配置让截断离开了当时的样本，没有改掉"两样东西共用一个计数器"。

## 六、收束

两单可以收成两句。

每轮重复的失败，记录在 checkpoint 里，随状态传到下一轮，重启清不掉。做法是换时机：状态还没对齐的那一刻不改历史，下一轮开头、调用模型之前再补；并且这次写出去的记录，不能成为下一次修复的输入。

参数残缺来自分片顺序和共享额度。逐个 chunk 判断"完整了没有"，在单片上看不到答案，所以第六个补丁之后要把判断放到整条流结束。额度是共享的。长思考和大输出单独看都在限额内，合在一起才把参数后半段截掉。

下次遇到同类故障，按这个顺序问：

1. **协议的不变量是什么？执行能保证它吗？** 不能，就规定补配对的时机和形态，不要等请求被拒绝之后再定。
2. **这次修复写出去的记录，会成为下一轮的输入吗？** 会，就检查它会不会让下一轮再次失败。写进消息表还是只写进 checkpoint，按读者分开。
3. **这是第几个补丁？** 第三个，停手，把判断挪到正确的粒度上。
4. **偶发的背后，哪一种资源是共享的、有上限的？** 先把额度列出来。

下一篇往下看行动落在哪里：沙箱。一台用户一台虚拟机的粒度、数据跟人走的存储迁移、三级休眠，以及一条命令从模型意图走到进程之前的全部步骤。平台怎样因为自己的保护逻辑停摆——事件循环被阻塞，以及巡检把还在输出的轮次判死——在第七篇。
